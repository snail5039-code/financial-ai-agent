# 자연어 투자 에이전트

> "SK하이닉스 4주 사줘", "삼성전자 사도 돼?"처럼 말로 하면 **투자 AI가 제안하고 → 검증 AI가 원문을 다시 확인하고 → 사용자가 승인한 주문만 사용자 폰에서** 증권사로 나가는 앱.

LLM이 돈을 다룰 때 생기는 문제(지어낸 숫자, 근거 없는 확신, 키 유출, 사용자가 모르는 주문)를 **구조로 막는 것**이 중심이다.

|---|---|
| 모의 자동매매 하루 (10/8, 사람 개입 없음) | 매수 4,727,750원 → **−1.52%**, 같은 날 코스피 **−2.62%** |

| 모의 자동매매 3일차 (10/13, 코스피 −5.46% 날) | AI가 매도 8건(절반씩 나눠 팔기), 매수 0건. 하루 **−1.78%**, 3일 누적 계좌 **−5.22%** vs 코스피 **−11.30%** |

## 1. 실제로 돌려 본 결과: 10/8 모의 자동매매

KIS 모의계좌(1,000만 원)로 장 시작부터 마감까지 앱이 **사람 손 없이** 종목 선정 → 투자 AI 제안 → 검증 AI 확인 → 한도 검사 → 주문까지 했다.

### 성과

| 종목 | 수량 | 평균 매입가 | 종가 | 평가손익 | 종목 등락 | 동종 업종 평균 |
|---|---|---|---|---|---|---|
| 현대건설 | 22 | 106,700 | 106,800 | **+2,200 (+0.09%)** | −3.70% | 건설 −4.10% |
| NH투자증권 | 93 | 25,595 | 24,800 | **−73,950 (−3.11%)** | −6.59% | 증권 −3.19% |
| **합계** | | | | **−71,750 (−1.52%)** | | 코스피 −2.62% |

- 계좌 전체 기준 −0.72%. 종가 기준 **미실현** 손익이다 (10/9 휴장, 매도는 10/12)
- 우리는 매수 시점(09:26~09:31)부터 종가까지, 코스피는 전일 종가 대비라 기간이 다르다. 참고용 비교다
- 출처: KIS 모의투자 일별 시세·잔고, 서버 DB의 제안서·검증·주문 기록

### 원인 분석 (손실 −71,750원)

| 원인 | 숫자 | 시스템이 봤나 |
|---|---|---|
| 시장 전체 급락 | 코스피 −2.62%, 3거래일 −5.4%, 외국인 −2.4조·기관 −1.9조 순매도 | ❌ 지수·수급 데이터 없음 |
| NH투자증권 업종 악재 | 증권 평균보다 −3.4%p 더 빠짐. 당일 아침 실적 우려·목표주가 4만→3.4만 원 | ❌ 뉴스 없음 |
| 장중 하락을 보고도 매수 | 09:27에 이미 −3.39%. 투자 AI가 반대 근거로 적고도 매수 | ✅ 봤지만 "사용자 지시"로 처리 |
| 선정 기준에 수익 신호 없음 | "최근 공시 순"으로 고름. 현대건설은 한 달 −18% 하락 추세 | ❌ 추세 안 씀 |
| 하루 늦은 가격 | 아침 분석이 10/6 종가(112,900원) 사용 | ❌ |

**결론**: 주문 과정(근거 확인·한도·중복 방지)은 설계대로 작동했고, 틀린 숫자로 나간 주문은 0건이다. 하지만 **무엇을 언제 살지 정하는 전략에 수익 근거가 없었다**. 손실은 거의 시장 분위기와 한 종목의 업종 악재로 설명된다.

### 분석으로 바꾼 것 → 그날을 다시 돌려 보니

| 원인 | 바꾼 것 |
|---|---|
| 장중 하락을 보고도 매수 | 자동 주문을 사용자 지시와 구분, 투자 AI가 "관찰"로 거절 가능 |
| 뉴스 없음 | Google 뉴스 RSS(무료)를 출처로, 악재는 반대 근거로 |
| 보유 중 급락 | 장중 −3% 하락 시 AI가 매도 판단 (종목당 하루 3번) |
| 매도가 막힘 | 매도도 매일 아침 사용자 승인, 나눠 팔기 |
| 선정 기준 근거 없음 | 백테스트로 규칙 검증 (3장) |

**재현**: 10/8 첫 자동 매수 때 AI가 본 자료를 그대로 넣었다. 자료는 공시·재무·종가와 폰이 보낸 현재가·1분봉이다. 여기에 지금 로직을 적용해 종목마다 3번씩 다시 돌렸다. 뉴스는 매수 시각 전에 나온 기사만 넣었다 (미래 정보 없음).

| 종목 (그때 상황) | 그때 자료만 | + 매수 전 뉴스 | 그날 실제 | 그날 종가 손익 |
|---|---|---|---|---|
| 현대건설 (09:26, 장중 −3.70%) | 관찰 3/3 | 관찰 3/3 | 매수 | +2,200 |
| NH투자증권 (09:27, 장중 −3.39%) | 관찰 3/3 | 관찰 3/3 | 매수 | −73,950 |

- **12번 모두 "지금은 사지 않고 관찰"**. 뉴스가 없어도 로직 변경만으로 하락 중인 매수를 거른다
- 뉴스를 넣으면 근거에 "거래대금 감소로 3분기 실적 눈높이 하향" 보도가 들어간다 (그날 NH 추가 하락의 원인)
- **이것은 수익이 아니다**: 사지 않았으니 손실도 수익도 없다. 확인한 것은 "10/8 손실의 원인이 된 판단(하락 중 매수)을 이제 거른다"는 것뿐이다
- 오르는 날에도 사는지, 즉 너무 조심해서 기회를 놓치지 않는지는 미확인이다. 수익은 여러 날의 실제 모의 자동매매로 검증한다 (10/12부터)

### 1·2일차에서 배운 것 → AI를 이렇게 고쳤다

두 날의 공통 원인은 **AI가 시장 전체를 못 본 것**이었다. 10/8은 코스피 −2.62% 날 하락 중에 샀고, 10/12는 코스피 −3.65%(4거래일 연속 하락) 날 보유 종목을 계속 들고 있었다.

| 드러난 문제 | 고친 방법 | 확인 |
|---|---|---|
| 시장 지수를 안 봄 | 폰이 KIS 지수 API(현재지수·일자별지수)로 코스피·코스닥 지수, 등락률, 오른/내린 종목 수, 최근 25거래일 종가를 받아 분석 때 보낸다. 서버는 키 없이 받기만 한다 | 모의투자에서 두 API 응답 확인 |
| 며칠 흐름을 모름 | 서버 코드가 1·5·20거래일 등락률과 연속 하락일을 계산해 출처 `market:KOSPI`로 준다. 숫자는 AI가 아니라 코드가 계산 | 10/12 실제 지수로 테스트: "5거래일 −8.42%, 4거래일 연속 하락" |
| 시장 급락을 근거에서 빠뜨림 | 투자 AI 지시: 시장이 크게 빠지면 매수는 관찰, 보유는 줄일지 판단. 검증 AI 지시: 시장 급락을 위험에서 빠뜨리면 지적 | 장 마감 후 실제 앱 분석: 투자 AI가 `market:KOSPI` 출처로 "코스피 −3.65%, 4거래일 연속 하락, 내린 종목 720개"를 근거·위험에 쓰고 **관찰** |
| 시장 급락에도 30분을 기다림 | 코스피 −1.5% 아래(지난 알림보다 1%p 더 빠질 때마다)면 보유 종목 전부를 바로 AI에게 다시 묻는다 | 앱 테스트 |
| 매도는 전부 아니면 0 | 투자 AI가 매도 수량을 전부/절반 중 고르고, 앱은 그만큼만 판다 (1주면 전부) | 앱 테스트 |
| 한도 실패를 "보유 판단"으로 기록 | 실패는 따로 기록하고 질문 횟수에서 뺌, 서버 분석 한도 20 → 100 | 장중 수정 후 14:04부터 정상 판단 |
| 급락 종목을 11분마다 다시 물음 | 지난번보다 1%p 더 빠졌을 때만 다시, 아니면 30분 주기 | 앱 테스트 |

- 매수·매도 기준을 숫자 규칙으로 정하지 않고, **AI가 볼 자료를 늘리고 검증 AI가 확인하게** 했다
- 효과는 아직 모른다. 내일부터 같은 방식으로 모의 자동매매를 이어서 확인한다

### 검증을 믿을 수 있었나: 1·2일차 제안·검증 46건 다시 보기

장중에는 "검증 AI 승인"을 믿고 사고팔았다. 끝나고 기록을 하나씩 다시 보니 **승인됐지만 빠진 것이 있는 제안**이 많았다.

| 이렇게 제안·검증했는데 | 나중에 보니 빠진 것 | 신뢰도 문제 | 고친 것 |
|---|---|---|---|
| 셀트리온 매수 3건 "조건부 승인" (10/12) | 조건이 "영업이익 숫자를 원문에 맞게 고쳐라", "뉴스 말고 공시를 인용하라". 틀린 제안이었다 | 고쳐야 할 제안이 통과했고, 자동매매는 **조건을 확인하지 않고** 20주를 샀다 | 자동 매수는 "승인"만. 숫자·출처를 고쳐야 하면 조건부가 아니라 반려 |

## 4. 성향 신호 파인튜닝

퀴즈 규칙은 "다음 달 방 빼야 하는데 그 돈 굴려볼까" 같은 말을 못 본다. 그래서 문장에서 위험 신호 6종(생활비·빌린 돈·급등 추격·공포 매도·몰빵·없음)을 고르는 모델을 학습했다.

| 방법 | test (293) | hard (57) | 위험 놓침 | 문장당 |
|---|---|---|---|---|
| 키워드 규칙 | 49.5% | 24.6% | 40.3% | 0ms |
| Gemini 프롬프트 | 92.2% | 100% | 0.4% | 1,335ms |

## 5. LangGraph: 대화가 주문이 되기까지

```
사용자 말 → rewrite("그거" 풀기) → classify ─┬ 조회    → fetch 멈춤 → 폰이 증권사에서 잔고·시세를 읽어 답함
                                              ├ 분석    → gather → 투자 AI → 검증 AI ─(반려)→ 투자 AI (최대 2번) → 기록
                                              ├ 주문    → 종목 → 정정·취소 대상 | 예약·분할 → 계좌(fetch) → 가격
                                              │           → gather → 투자 AI → 검증 AI → 정책 검사(코드) → approval 멈춤 → execute 멈춤 → 체결 기록
                                              └ 결과·기록·용어 → DB 기록으로 답 (LLM은 분류만)
```

- **멈춤(interrupt) 4종류로 "서버는 키가 없다"를 구현**했다. 증권사 일이 필요하면 서버 그래프가 멈추고, 폰이 답해야 다음으로 간다
  - `fetch`: 잔고·시세 조회 (2곳)
  - `approval`: 사용자 승인 (1곳)
  - `execute`: 폰이 주문 (1곳)
  - `question`: 되묻기 (6곳)
- **Postgres 체크포인트**: 멈춘 그래프 상태를 DB에 저장해서 앱을 껐다 켜도 승인 대기 대화가 이어진다
  - 10/8 재현 때도 체크포인트에서 그날의 현재가·1분봉을 그대로 꺼내 썼다
- **분석 노드 재사용**: 주문 그래프는 분석과 같은 노드(gather → 투자 AI → 검증 AI)를 그대로 쓴다. 분석 직후 주문이면 그 검증 결과를 이어 쓴다. 그래서 직접 지시한 주문도 자동매매 주문도 검증 없이 처리안이 될 수 없다
- **LLM 호출은 한 파일(`llm.py`)에만**: 요청 이해("그거" 풀기·분류·값 뽑기)를 3번에서 1번 호출로 합쳐 6~10초 → 약 1.4초로 줄였다. 테스트는 이 파일만 가짜로 바꿔 비용 0으로 돈다

## 6. RAG: 공시 원문을 근거로

| 항목 | 값 |
|---|---|
| 대상 | 코스피 100 + 코스닥 50 (151종목), 공시 11,967건 |
| 본문 | 정기보고서 최신 2건 + 주요사항보고서 3건 → **29,352조각** (표 보존 조각 14,251) |
| 임베딩·검색 | Gemini embedding 768차원, PostgreSQL pgvector (코사인 거리) |
| 한 번의 분석에 넣는 자료 | 종가, 재무제표, 최근 공시 5건, **본문 조각 최대 6개**, 뉴스 5건, 현재가·1분봉, 계좌 |

- **검색**: 요청 문장과 고정 관점 3개(실적과 수익성, 위험 요인, 사업 전망)로 4번 찾는다. 질문이 좁아도 위험 요인이 빠지지 않게 하려는 것이다
  - 절대 기준(거리 0.6 이하)과 상대 기준(그 검색의 1등 + 0.05 이내)으로 관련 없는 문단을 버린다. 기준값은 실측으로 정했다 (관련 문단 0.33~0.56)
- **겪은 문제**: 벡터 색인(HNSW)이 전체에서 가까운 것을 먼저 고른 뒤 종목으로 걸러서 150종목 중 115종목은 결과가 비었다
  - 그 종목 조각만 먼저 고르고 거리를 정확히 재는 방식으로 바꿔 해결했다 (종목당 수백 조각이라 빠름)
- **출처 ID로 인용하고 검증 AI가 다시 읽는다**: 조각마다 `dart:{접수번호}#{순번}` ID를 붙인다
  - 투자 AI는 근거마다 이 ID를 달고, 검증 AI는 투자 AI가 본 글이 아니라 **ID로 원문을 다시 불러와** 대조한다
  - 없는 ID는 코드가 막는다. 평가에서 투자 AI가 지어낸 출처 ID를 실제로 잡았다
- 표가 문장으로 깨지지 않게 "[표] 항목 | 값" 형태로 보존하는 청킹을 만들었다. 10/12 재임베딩으로 조각이 12,974 → 29,352개가 됐다 (재무 표가 숫자 그대로 검색됨)

## 7. 설계

| 원칙 | 구현 |
|---|---|
| 서버는 증권사 키를 모른다 | 키는 폰 보안 저장소에만. 서버는 처리안까지, 주문은 폰이 직접 |
| 모든 주문은 3단계 | 투자 AI → 검증 AI → 사용자 승인. 자동매매·정정·취소도 같은 길 |
| 검증 AI는 독립적 | 결론 없이 제안·출처 ID만 받아 원문을 다시 읽고 판정 |
| 숫자는 코드가 | LLM은 분류·문장만. 금액·한도·수수료는 코드가 계산 |
| 기본은 모의투자 | 실전 모드는 직접 켜야 하고(모의 체결 10건·5일 이상), 실전 자동매매는 1회 30만 원 |
